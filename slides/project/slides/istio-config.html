METODOLOGIA DE TESTES: PROTÓTIPO, CONFIGURAÇÃO DO ISTIO

Arquivos de configuração no lugar de código

  • Ligar o Istio: um rótulo no namespace faz o Istio colocar o proxy em cada pod.
  • Criptografia obrigatória: uma regra exige que toda conexão use certificado (mTLS).
  • Controle de acesso: uma regra diz que só o frontend pode chamar o catalog.
  • Tempo limite e nova tentativa: nenhuma chamada espera mais de 1 segundo.
  • Divisão de versões: 90% dos pedidos vão para a versão 1 e 10% para a versão 2.

kind: AuthorizationPolicy
spec:
  selector: {app: catalog}
  action: ALLOW
  rules:
  - from: principals:
    [".../sa/frontend"]

Exemplo: a regra de acesso do catalog, em sete linhas.

Este é o coração da parte do Istio. Tudo o que no caso B virou código Go, no caso C virou arquivo de configuração em YAML. Um rótulo no namespace liga o Istio. Uma regra chamada PeerAuthentication exige criptografia em toda conexão. Uma AuthorizationPolicy, que é o exemplo à direita, diz que o catalog só aceita chamadas que venham do frontend, usando a identidade que o próprio Istio dá a cada serviço. Um VirtualService define o tempo limite de 1 segundo, a nova tentativa e a divisão entre as versões. E uma DestinationRule limita conexões. Somando tudo, foram 31 linhas.
